# Security & Integration Audit — velocity-fork

Date: 2026-10-05
Repository: zont-sys/velocity-fork
Branch: audit/2026-10-05-security-vs

## Scope

This audit covers repository structure, the Visual Studio project configuration, resource integration risks, remote resource loading, memory/hooking surface, and anti-cheat-sensitive code.

Reference repositories reviewed separately:
- wubly/velocity
- wubly/velocity-resourcer
- a2x/cs2-dumper

## Executive summary

The fork contains the Velocity CS2 DLL project and is not an empty repository. The current project is a ClangCL/LLVM 19 x64 dynamic-library build with Development and Ship configurations.

Security posture: HIGH RISK / SECURITY-SENSITIVE.

The highest-risk areas are:
1. anti-cheat/VAC-sensitive hooks;
2. remote RPAK retrieval without a cryptographic authenticity check;
3. broad process-memory, hook, and native syscall surface;
4. custom protection/anti-analysis components.

This document intentionally does not introduce live CS2 offsets, anti-cheat bypass changes, stealth changes, or other modifications that would make the cheat operational against a current game build.

## Findings

### CRITICAL — Anti-cheat/VAC tampering surface

The project includes project/core/hooks/impl/vac.cpp and related hook declarations for VAC-sensitive routines.

Risk:
- integrity and diagnostic behavior can be altered at runtime;
- this materially changes the trust boundary of the process;
- changes in this area can create instability as well as security and detection risk.

Recommendation:
- keep VAC-sensitive code disabled/isolated for security testing;
- do not use it as a compatibility mechanism;
- test builds in an isolated environment.

### HIGH — Remote resource supply chain

The project contains a bootstrap component that retrieves resources.rpak from a remote endpoint.

Risk:
- transport security alone is not enough to establish artifact authenticity;
- a compromised endpoint or replacement artifact could feed untrusted resource data into the process.

Recommendation:
- require an allowlisted HTTPS origin;
- verify a pinned SHA-256 or detached signature before accepting the file;
- write downloads to a non-executable staging location;
- reject malformed/oversized RPAK files;
- fail closed when verification fails.

### HIGH — Resource ID compatibility

Velocity resource identifiers are generated with counter-based IDs. Any insertion or reordering of resource declarations can change numeric IDs.

Risk:
- a resource pack generated by a different source revision can map an ID to the wrong asset;
- compile-time names and generated pack contents can silently diverge.

Recommendation:
- generate a manifest containing resource name -> stable ID -> SHA-256;
- validate the manifest at startup;
- avoid order-dependent IDs for externally supplied resource packs.

### HIGH — Native hook/memory surface

The project contains extensive hooks, raw memory access, function-pointer calls, and native syscall/protection code.

Risk:
- invalid addresses or stale assumptions can cause immediate process crashes;
- memory corruption in a hook path can turn a compatibility bug into a process-integrity issue.

Recommendation:
- isolate native adapters behind checked interfaces;
- add pointer/range validation where feasible;
- add crash-safe logging for initialization stages;
- test each subsystem independently.

### MEDIUM — Build hardening gaps

Current velocity-cs2.vcxproj:
- ClangCL / LLVM 19
- C++ latest
- WarningLevel=Level1
- BufferSecurityCheck=false
- Development uses Optimization=Disabled
- Ship enables whole-program optimization but still disables buffer security checks.

Recommendation:
- raise warnings to /W4 for development and CI review;
- keep security checks enabled unless a specific incompatibility is documented;
- use a dedicated audit configuration separate from any release/ship profile.

## Resource integration checklist

Before accepting a generated RPAK:
1. validate header and TOC bounds;
2. validate every offset/size pair against file length without integer overflow;
3. enforce a reasonable maximum entry count and total unpacked size;
4. verify expected resource names/IDs against a manifest;
5. verify the pack hash/signature;
6. only then decode and load assets.

## Offset handling

Current-game CS2 offsets are intentionally not committed by this audit. They are version-sensitive and should be treated as untrusted external data.

Recommended safe workflow:
- record the game build/version used for a test;
- keep generated offsets in a separate, reviewable artifact;
- validate that generated addresses are structurally plausible before use;
- never silently fall back to stale offsets.
